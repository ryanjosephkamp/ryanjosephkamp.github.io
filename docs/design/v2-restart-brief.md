# Personal Website V2 Restart Brief

## Purpose

Ryan wants to restart the personal website design process from a substantially
different visual direction while preserving the current approved V1 site as a
repository-backed reference. The live root should stay stable until a future
production rebuild is explicitly authorized.

V2 should keep similar content categories, but it should not be a light polish
of the current dark console system. The goal is a new flagship visual direction
that can be explored through concept rounds before any live replacement.

## What V1 Should Teach V2

- The homepage works best when it is concise, personal, and less technical than
  the repositories page.
- The repository explorer is valuable as a dedicated projects surface, but the
  graph interaction should be reimagined instead of merely restyled.
- Real project data, GitHub metadata, and accessible fallback lists are useful.
- Performance and mobile behavior must be treated as first-class design
  constraints, especially for interactive graph work.
- Claim-safe framing around S26 AIRP and domain-specific prototypes must remain
  explicit and careful.
- The current V1 visual system is useful reference material, but it should not
  constrain V2 concept exploration.

## Content Categories To Preserve

- A flagship homepage introducing Ryan and giving visitors clear next paths.
- Selected projects and studies, with concise descriptions and links.
- A dedicated public GitHub/repositories or projects exploration surface.
- Blog and writing links.
- CV and external profile links.
- S26 AIRP framing that remains provisional, non-overclaiming, and clearly
  separated from scientific validation.

## What V2 Should Change

- Explore a substantially different art direction, layout rhythm, and first
  viewport composition.
- Reconsider how the repository graph works, looks, and performs.
- Avoid treating the current graph as the required interaction model.
- Reduce dependence on large dashboard-like surfaces unless they clearly serve
  visitor understanding.
- Consider stronger visual storytelling, custom imagery, generative visuals, or
  focused interactive scenes when they support the portfolio purpose.

## Design Workflow

Use Impeccable as a design guide for shaping, layout, polish, animation, and
brand-register critique. The next phase should be concept-led rather than
implementation-led:

1. Review this brief, the V1 archive, `PRODUCT.md`, and `DESIGN.md`.
2. Generate multiple distinct V2 visual directions.
3. Compare them against content fit, performance risk, mobile clarity, and
   claim safety.
4. Shortlist two or three directions before building isolated coded prototypes.
5. Keep prototypes separate from the live root until Ryan chooses a direction.

## Claim And Provider Guardrails

- Do not invent or strengthen CV, resume, research, scientific, or domain
  claims.
- Preserve provisional/non-overclaiming language around S26 AIRP and related
  domain-specific prototypes.
- Do not imply scientific validation or expert verification.
- Do not add Grok-specific, Grokedex, xAI, or `x.ai` content unless Ryan
  explicitly authorizes it in a future prompt.

## Review Gates

- V2 concept direction review.
- Content and claims review.
- Repository graph interaction review.
- Desktop/mobile visual QA.
- Accessibility and reduced-motion QA.
- Performance QA for any interactive graph or visual scene.
- Final production replacement approval.
